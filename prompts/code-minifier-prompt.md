# Claude Code Prompt — Build Tool #25: Code Minifier / Beautifier (JS/CSS/HTML)

Run after tool-shell and tools #1-24 exist. Covers three languages in one
tool via three well-established, purpose-specific libraries — no single
library does all three well.

---

```
Build the Code Minifier & Beautifier for the Aakasa Toolbox monorepo.

CONTEXT:
- Route: apps/web/app/tools/code-minifier/
- Uses <ToolShell> and TOOL_REGISTRY as established.
- 100% client-side. Use dedicated libraries per language rather than one
  generic tool — install:
  - `js-beautify` — handles both beautify AND minify-adjacent needs for
    JS/CSS/HTML beautification (has js_beautify, css_beautify, html_beautify)
  - `terser` — for genuine JS minification (js-beautify's "minify" isn't a
    real minifier; terser does actual dead-code-aware minification with
    proper mangling)
  - `clean-css` — for genuine CSS minification
  - `html-minifier-terser` — for genuine HTML minification
  Check bundle size impact of loading all of these — since this tool
  supports three languages with separate beautify/minify libraries each,
  consider dynamic imports per-language-tab so a user working only in CSS
  mode doesn't pay the bundle cost of the JS/HTML libraries they're not
  using. This is worth actually implementing (route-level code splitting is
  standard Next.js behavior, but WITHIN this one tool's component, dynamic
  `import()` per active language tab is the relevant technique) rather than
  bundling all four libraries into one eagerly-loaded chunk.
- Design tokens as established; input/output panes in font-mono.

STEP 1 — Register:
  { slug: 'code-minifier', title: 'Code Minifier & Beautifier',
    shortDescription: 'Minify or beautify JavaScript, CSS, and HTML instantly.',
    category: 'developer', tier: 'free' }

STEP 2 — page.tsx: standard metadata + ToolShell. relatedTools:
['json-formatter', 'sql-formatter', 'html-entity-tool']. FAQ (3-4 Q&A): the
difference between minification (removing whitespace/shortening names for
smaller file size, machine-optimized) and beautification (the opposite,
human-readable formatting), why minified JS specifically also involves
variable renaming/mangling (not just whitespace removal, genuinely reduces
size further, but makes debugging minified output difficult without a
source map — mention source maps are NOT generated by this tool, it's a
one-way transform for quick use, not a production build pipeline
replacement), a note on when to use each (minify for production asset size,
beautify for reading/debugging unfamiliar or minified code), and the
privacy note.

STEP 3 — CodeMinifier.tsx:
- Language tabs: JavaScript / CSS / HTML.
- Mode toggle: Minify / Beautify.
- Input textarea (font-mono), output panel (font-mono, read-only).
- Beautify options (per language, only show what's relevant to the active
  tab): indent size, indent with spaces vs tabs, brace style (for JS/CSS).
- Minify options: for JS specifically, expose whether to enable
  mangling/variable-renaming (on by default for max size reduction, toggle
  off if the user wants whitespace-only minification without renamed
  variables — useful for slightly more debuggable minified output).
- Size comparison: show original size vs. output size and percentage
  change, consistent with the stat-display pattern established in Image
  Compressor and Word Counter.
- CopyButton and Download (matching extension: .js/.css/.html) on output.
- Sample code button per language (a small representative snippet — for JS,
  something with a function and a variable that visibly gets renamed on
  minify, so the mangling behavior is visible, not just whitespace removal).
- Error handling: JS minification via terser can genuinely fail on invalid
  JS syntax (it needs to parse the code) — catch and surface terser's error
  message clearly, including line/column if terser provides it. CSS/HTML
  minifiers are typically more lenient/best-effort; confirm and handle
  accordingly per library rather than assuming uniform error behavior
  across all three.

STEP 4 — Logic separation: apps/web/app/tools/code-minifier/utils/
codeTransform.ts — separate typed async functions per language/direction:
minifyJs, beautifyJs, minifyCss, beautifyCss, minifyHtml, beautifyHtml, each
returning { result: string; error?: string }. Handle the dynamic-import
pattern for the underlying libraries within these functions so the
component itself doesn't need to manage lazy-loading directly.

STEP 5 — Verify: registry entry resolves.

After building, tell me:
1. Confirm dynamic imports were actually used so switching to, say, the CSS
   tab doesn't eagerly load terser/html-minifier-terser — describe the
   approach taken and roughly how much bundle size this saves per
   language tab versus eagerly bundling all four libraries together.
2. Confirm terser's error handling surfaces a specific, useful message on
   genuinely invalid JS input (test with a deliberately broken snippet, e.g.
   an unclosed function) rather than a generic failure.
3. Confirm minified JS output actually differs meaningfully with mangling
   on vs. off (test the same input both ways and describe the size
   difference) so the toggle is confirmed to do something real, not just
   exist as an inert UI control.
```

## Note
This tool bundles four separate transformation libraries for three
languages — the bundle-size/dynamic-import consideration is worth taking
seriously here specifically, more than in most prior tools, since eagerly
loading terser + clean-css + html-minifier-terser + js-beautify all at once
on page load would be a meaningfully heavier payload than any tool built so
far for a page most visitors will only use one-third of (one language) per
visit.
